noti-fi panel: three ways to redesign each part

The goal: almost nothing is typed. Every setting that expects a known kind of value becomes a choice (chips, swatches, pickers, sliders with named stops), free text is only for names and genuine search, and every change shows its effect at once. Each section below has three structures; the one marked Recommended is my pick, and they mix and match (an option from one section does not force one in another).

The review of these options and the combined design for each part is in ui-redesign-combined.html.

2. App shell and navigation

Today: a Kirigami drawer with nine pages, and Routing with its own side panel inside it (two levels of side navigation).

One sidebar with headed groups: Now (Overview, History) · Where it goes (Apps, Zones, Rules) · Look & quiet (Appearance, Focus) · App (Settings, System). Routing's inner panel goes away.

  • One level of navigation; everything one click away
  • Groups explain what each page is for
  • Apps/Zones/Rules lose the shared "Routing" toolbar (Save moves to a global bar)

B. Task home screen

Move popups
Change the look
Focus time
Find a missed one

The first screen is a grid of tasks in plain words; each opens the page already in the right state (e.g. "Quiet an app" opens Apps with search focused).

  • Easiest for a first-time user
  • Pages can stay as they are behind it
  • An extra click for regular users
  • Overview's live status needs a home elsewhere

C. Top tabs + contextual side panel

Four top tabs (Status · Routing · Look · Settings); each tab has its own short side list (Routing: Apps, Zones, Rules).

  • Matches System Settings-style apps; scales if pages are added
  • Two levels again; the problem we are trying to remove

13. UI stack

Recommendation: no new stack. Stay on Qt/QML + Kirigami and add Kirigami Addons. Every option above can be built on it, and nothing else matches it on Plasma's look, screen-reader support and the tray. Versions checked on 2026-11-06 from the projects' own release pages.

How it fits in. Kirigami Addons is a plain QML module (import org.kde.kirigamiaddons.formcard). The panel's existing engine finds it on the system import path, so nothing changes in the Rust code. It is already installed here (kirigami-addons 1.15). It becomes a runtime dependency in PKGBUILD and install.sh. KDE's newer Kirigami Forms module (the API System Settings is moving to) is the long-term target once the minimum Frameworks version ships it; FormCard is not deprecated meanwhile.
Three small components to build ourselves (none exist in any stack): a chip input with autocomplete (already started as the Rules tags), a segmented control, and the drag-to-place screen map (started on Zones).
If a rewrite were ever wanted, Slint is the only credible alternative, but it would mean hand-making more controls than today for a less native result.
